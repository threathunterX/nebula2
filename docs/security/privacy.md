# 隐私设计与合规

风控系统天然处理大量个人信息——IP 地址、设备标识、账号、手机号、银行卡、地理位置,乃至完整的请求体与响应体。这使得隐私保护不是附加功能,而是**架构约束**。

本文说明星云 2.0 如何在系统层面落实这些约束。

---

## 一、数据分级

每个事件字段在 [domain-schema](../../packages/domain-schema/) 中都必须标注敏感级别:

| 级别 | 含义 | 处理方式 | 典型字段 |
|---|---|---|---|
| `public` | 公开信息 | 明文存储 | `status`、`method`、`s_bytes` |
| `internal` | 内部信息 | 明文存储,访问需授权 | `host`、`uri_stem`、`referer` |
| `pii` | 个人信息 | HMAC 或加密列存储,查询需授权并审计 | `c_ip`、`uid`、`did`、`geo_city` |
| `sensitive` | 敏感个人信息 | **采集端即脱敏,原文不落库** | `c_body`、`s_body`、`cookie`、`uri_query`、口令、证件号、银行卡 |

schema 强制约束:标注为 `sensitive` 的字段,`masking` 不允许为 `none`。这条规则由 CI 校验,不满足则构建失败。

---

## 二、采集端脱敏

脱敏发生在 **collector 内部**,即数据离开客户网络边界之前。这是与 1.x 最重要的差别——1.x 虽然在字段注释里写了"脱敏",但没有系统化的机制,实际是否脱敏取决于各个 parser 的实现。

支持的脱敏方式:

| 方式 | 行为 | 适用 |
|---|---|---|
| `drop` | 整个字段丢弃 | 口令、支付凭证 |
| `hash` | 替换为 HMAC-SHA256(密钥可轮换) | 需要做关联分析但不需要还原的标识符 |
| `partial` | 保留部分字符,其余掩码 | 手机号 `138****8000`、卡号后四位 |
| `regex` | 按正则匹配替换 | 请求体中的结构化敏感字段 |

默认规则从严:`c_body`、`s_body`、`cookie` 默认整体丢弃,`uri_query` 默认对常见敏感参数名(password、token、id_card、mobile、card_no 等)做正则脱敏。

**放宽默认规则需要显式配置,且该配置项本身会被记录进审计日志。**

```yaml
# collector 配置示例
masking:
  fields:
    c_body:    { action: regex, pattern: "(password|passwd|pwd)=[^&]*", replacement: "$1=<REDACTED>" }
    cookie:    { action: drop }
    uri_query: { action: regex, pattern: "(token|id_card|mobile)=[^&]*", replacement: "$1=<REDACTED>" }
  identifiers:
    uid: { action: hash, key_ref: "env:NEBULA_HMAC_KEY" }
```

## 三、存储与访问

**标识符加密**:标注为 `pii` 的字段以 HMAC 形式存储。HMAC 密钥独立于数据库,支持轮换(轮换期间新旧密钥并存,便于平滑过渡)。这意味着即使数据库被拖库,攻击者也无法直接得到原始账号或设备 ID。

**保留期自动执行**:由 ClickHouse 的 TTL 与 PostgreSQL 的分区裁剪自动完成,不依赖运维脚本。

| 数据 | 默认保留期 | 可配置范围 |
|---|---|---|
| 事件明细 | 30 天 | 7 ~ 180 天 |
| 小时聚合 | 90 天 | 30 ~ 365 天 |
| 风险告警 | 90 天 | 30 ~ 730 天 |
| 长期画像 | 180 天 | 30 ~ 730 天 |
| 审计日志 | 730 天 | ≥ 180 天 |

> 1.x 的清理逻辑是一段 crontab 脚本,其中一条规则是「磁盘占用超过 80% 就删掉最旧的 5 个目录」——会静默删除未过期数据,同时在磁盘充足时又不保证过期数据被删除。2.0 改由存储层 TTL 保证,两个方向的问题都不再存在。

**访问控制与审计**:查询个人信息需要相应权限,且每次查询记录操作者、时间、查询条件与命中量。审计日志独立存储,普通管理员不可删除。

## 四、数据主体权利

提供接口支持个人信息主体行使权利:

```
GET    /api/v2/privacy/subject/{type}/{value}/export   导出该主体的全部数据
DELETE /api/v2/privacy/subject/{type}/{value}          删除该主体的全部数据
```

`type` 取值为 `uid` / `did` / `ip`。删除操作会同步清理事件明细、聚合结果、画像与名单,并记录审计。

> 注意:删除请求本身需要经过身份核验,该流程由部署方按自身合规要求实现,系统只提供执行能力。

## 五、合规对齐

### 中国大陆

| 法规 | 相关要求 | 系统支持 |
|---|---|---|
| 个人信息保护法 | 最小必要、告知同意、保留期限、主体权利 | 字段分级 + 采集端脱敏 + TTL + 主体权利接口 |
| 数据安全法 | 数据分类分级、安全保护义务 | 四级分类体系、加密存储、审计 |
| 网络安全等级保护 2.0 | 身份鉴别、访问控制、安全审计、数据完整性 | Argon2id、RBAC、审计日志、TLS |

**风控场景的特别提示**:基于个人信息进行自动化决策(如自动阻断)时,个保法要求保证决策的透明度与结果公平,并向个人提供拒绝仅通过自动化决策方式作出决定的途径。这正是 2.0 落地告警可解释性(`explain`)的原因之一——每条风险判定都能还原出"依据哪些指标、超过了什么阈值"。部署方应据此设计申诉与人工复核流程。

### 出海场景

如需服务欧盟用户,还需评估 GDPR 的额外要求(法律依据、DPO、跨境传输、72 小时泄露通报)。系统提供的技术能力(脱敏、加密、保留期、主体权利、审计)是必要条件而非充分条件,合规判断需结合具体业务。

- 全部示例 IP 替换为文档专用段(RFC 5737 的 `198.51.100.0/24` 与 `203.0.113.0/24`)
- 全部示例域名替换为 `example.com` 系

审计过程与逐项改动记录见 [`seeds/INVENTORY.md`](../../seeds/INVENTORY.md)。
