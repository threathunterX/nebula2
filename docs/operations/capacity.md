# 容量规划

本文的数字**全部来自实测**,不是估算。测量环境与方法写在最后,你应当在自己的硬件上
重跑一遍 —— 下面给的是量级与**变化趋势**,不是可以直接照抄的配置表。

> **没测过的部分本文会明说。** 横向扩展、多节点 Flink、真实生产流量的分布特征都不在
> 这台机器能测的范围内。把没测过的写成结论,比不写更糟。

---

## 一、先看结论

| 组件 | 实测吞吐 | 主要成本来自 |
|---|---|---|
| 采集器 | **约 22 万条/秒**(单进程) | JSON 编解码 |
| 引擎(单线程,170 条策略) | **约 6 千条/秒** | 策略条数 × 每条的条件求值 |
| ClickHouse 事件明细 | **每条约 26 字节**(压缩后) | `attrs`、`uid`、`did`、`c_ip` |

**采集器不是瓶颈,引擎才是。** 两者差了 35 倍。规划时先算引擎要几个并行度,
采集器基本不用算。

---

## 二、采集器

20 万条事件(48.8 MB JSON Lines)跑三次,取中位:

| 配置 | 吞吐 |
|---|---|
| 加载事件模型 + 脱敏(`-events seeds/events`) | 22.2 万条/秒 |
| 不加载事件模型(不脱敏) | 21.5 万条/秒 |

**脱敏几乎不要钱。** 两者差异在测量噪声之内(带脱敏的那次甚至更快)。这条值得单独
说,因为直觉上会以为「逐字段查敏感级别再改写」很贵 —— 实际上瓶颈是 JSON 的解析与
序列化,脱敏只是在已解析的 map 上改几个值。

**推论:不要为了性能关掉脱敏。** 那省不下什么,却把 `sensitive` 字段放进了链路。

内存:采集器不持有状态,常驻内存与事件量无关。

---

## 三、引擎

这是要认真算的部分。全部测量都是**单线程**(`StrategyEngine.process`),生产部署由
Flink 按 key 分区并行,吞吐大致按并行度线性放大 —— **但这条没在多节点上验证过**。

### 3.1 策略条数是主导因素

事件 10 万条,IP 基数 250:

| 策略条数 | 吞吐 | 堆占用 |
|---|---|---|
| 10 | 7.1 万条/秒 | 48 MB |
| 50 | 2.3 万条/秒 | 115 MB |
| 170(全部内置模板) | 9 千条/秒 | 325 MB |

**大致与策略条数成反比。** 每条事件要在每条策略上求一次值,这是当前实现的直接
后果 —— 没有按触发事件建索引。

实践含义很直接:**别把 170 条模板全部上线。** 它们来自 1.x 某个站点的经验,是起点
不是标准答案。挑真正需要的那些,吞吐会成倍回来。

### 3.2 主体基数:高基数反而更快

事件 10 万条,全部 170 条策略:

| IP 基数 | 吞吐 | 堆占用 |
|---|---|---|
| 250 | 8.9 千条/秒 | 325 MB |
| 5 000 | 1.6 万条/秒 | 373 MB |
| 50 000 | 1.5 万条/秒 | 679 MB |

**这与直觉相反,值得解释:** 代价不在「有多少个 key」,而在「每个 key 的窗口里积了
多少条事件」。基数低意味着同一个 key 反复被命中,滑动窗口每次求值都要遍历更多元素。
基数高时事件摊薄到各个 key 上,单次求值反而便宜。

代价转移到了内存:基数从 250 涨到 5 万,堆从 325 MB 涨到 679 MB。

**所以压测时用低基数的合成数据会低估吞吐、低估内存** —— 两个方向都错。压测数据的
主体分布应当贴近真实流量。

### 3.3 状态规模怎么估

堆占用 ≈ 变量数 × 活跃 key 基数 × 每个窗口的元素数 × 单元素开销。

与其套公式,不如**用自己的策略集和贴近真实的数据实测**。基准程序怎么写见下方
[测量方法](#七测量方法) —— 几十行,改改参数就能跑。

## 四、存储

50 万条真实形态的事件(含 `attrs`、UA、地理字段),写进 ClickHouse 后 `OPTIMIZE FINAL`:

| 指标 | 实测 |
|---|---|
| 未压缩 | 145.6 MiB |
| 落盘(压缩后) | 12.6 MiB |
| 压缩比 | **11.6 倍** |
| **每条事件落盘** | **26.4 字节** |

占地方的列,从大到小:

| 列 | 压缩后 |
|---|---|
| `attrs` | 2.95 MiB |
| `uid` | 2.41 MiB |
| `did` | 2.41 MiB |
| `c_ip` | 2.25 MiB |
| `event_time` | 864 KiB |

`uid` / `did` 排在前面是因为它们已经是 **HMAC 后的 64 位十六进制串** —— 高熵,压不动。
这是[存储层 PII 保护](../security/privacy.md)的直接代价,写在这里让人知道它花了多少钱:
两列合起来约占总量的 38%。

### 按日增量推算

| 事件速率 | 明细日增量(压缩后) | 30 天保留期 |
|---|---|---|
| 1 000 EPS(约 8600 万/天) | 约 2.2 GB | 约 65 GB |
| 1 亿条/天 | **约 2.5 GB** | 约 75 GB |
| 10 亿条/天 | 约 25 GB | 约 750 GB |

小时聚合表(`events_hourly`)的量级取决于 `(event_name, c_ip, hour)` 的组合数,与明细
不成比例 —— **这一项没有实测**,因为它完全由流量的 IP 分布决定,合成数据测不出有意义
的数字。

## 五、扩容的顺序

按实测结论排:

1. **先减策略。** 从 170 条减到真正需要的几十条,吞吐成倍回来 —— 这是唯一不花钱的一步。
2. **再加引擎并行度。** Flink 按 key 分区,`c_ip` / `uid` / `did` 三个维度天然可分。
   注意并行度受限于 key 的基数:key 少于并行度时多出来的槽位空转。
3. **再看内存。** 高基数场景下堆比 CPU 先到顶,表现是 GC 时间上升而吞吐不涨。
4. **最后才是存储。** 26 字节/条,除非流量到十亿量级,存储不会先成为问题。

**采集器基本不需要扩。** 22 万条/秒的单进程吞吐,比引擎高 35 倍。

---

## 六、这台机器测不了的

如实列出来,免得有人把上面的数字当成生产结论:

- **多节点 Flink 的横向扩展比例。** 本机内存不足以起一个多 TaskManager 的集群,
  「吞吐按并行度线性放大」是**推断**,不是实测。
- **网络与 Kafka 的吞吐上限。** 全部测量都在单机内完成,没有跨网络的往返。
- **真实流量的分布特征。** 合成数据的主体分布是均匀的,真实流量是长尾的 ——
  长尾意味着少数 key 上的窗口远大于平均,而 3.2 已经说明窗口大小才是主要代价。
- **checkpoint 对吞吐的影响。** 本机测的是纯计算,没有 RocksDB 状态后端与周期性
  checkpoint。
- **告警表与聚合表的实际增量。** 取决于策略命中率与流量分布。

## 七、测量方法

**环境**:Apple M4(10 核)/ 16 GB / macOS 26.5 / Go 1.26.5 / OpenJDK 21.0.12 /
ClickHouse 24.8。同一台机器上没有其它负载。

**采集器**:生成 20 万条 JSON Lines 事件,`-source file -out /dev/null`,读退出摘要里
的「条/秒」。跑三次取中位。

**引擎**:一段几十行的 `Bench.java`,加载 `seeds/` 的全部策略与变量,构建变量图后
循环调用 `StrategyEngine.process`,计时并读 `Runtime` 的堆占用。参数是「事件条数 /
策略条数 / IP 基数」。

> 内置模板默认是 `test` 状态。测过一次:`test` 与 `online` 的吞吐、告警条数、堆占用
> 三项都一样(11.6k vs 12.1k 条/秒,均在噪声内)—— `test` 照常计算并产出告警,只是
> 标记 `test=true` 且不参与 `/checkRisk` 的决策。所以压测时不需要改状态。

**存储**:50 万条含 `attrs` 与 UA 的事件写入 ClickHouse,`OPTIMIZE TABLE ... FINAL`
之后查 `system.parts` 与 `system.parts_columns`。

> 基准程序**没有随仓库分发** —— 它是一次性的测量工具,留在仓库里会变成又一个需要
> 跟着接口变化维护的东西,而它的价值在于「跑一次拿到数字」。上面的描述足够重建它。
