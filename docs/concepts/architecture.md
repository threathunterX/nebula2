# 系统架构

## 总览

```
                    ┌──────────────── 控制面 ─────────────────┐
                    │  console-web    策略/变量/名单/报表 UI   │
                    │  console-api    元数据管理 · RBAC · 审计 │
                    └───────┬────────────────────┬────────────┘
                            │ 元数据下发          │ 查询
                            ▼                    ▼
业务流量/日志           ┌──────────┐        ┌──────────────┐
   │                   │PostgreSQL│        │  ClickHouse  │
   ▼                   │  元数据   │        │ 事件+聚合结果 │
┌───────────┐  Kafka   └──────────┘        └──────▲───────┘
│ collector │────┐                                 │
│   (Go)    │    │    ┌─────────────────────────┐  │
└───────────┘    ├───▶│      Flink 计算作业      │──┘
 SDK / HTTP ─────┤    │  ① 变量引擎              │
 Kafka / syslog ─┤    │  ② 规则引擎              │──▶ Kafka: notice
 Zeek(可选)─────┘    │  ③ 画像更新              │        │
                      └─────────────────────────┘        ▼
                                                  Redis 名单 + 处置动作
                                                         │
                                            /checkRisk ◀─┘  业务系统同步查询
```

架构上有一条贯穿的原则:**只保留一条计算路径、一个消息总线、一套存储**。1.x 在这三处都是双份(实时与离线两套引擎、babel 与文件落盘两条数据通路、LevelDB 与 Aerospike 与 MySQL 三套存储),它们之间的语义漂移是 1.x 大部分复杂度的来源。

## 数据面

### collector —— 采集

职责有三件:接入数据源、还原为标准事件、**脱敏**。

脱敏放在采集端而非计算端,是一个刻意的架构选择:它让敏感数据在**离开客户网络边界之前**就已经被处理,后续所有组件都不再接触原文。这样即使下游任何一环被攻破,泄露的也只是脱敏后的数据。详见[隐私设计](../security/privacy.md)。

采集器是无状态的,可以水平扩展。多实例采集同一数据源时,由 Kafka 的消费组保证不重复。

### Kafka —— 总线兼事件存储

Kafka 在架构中承担三个角色,这也是它取代 1.x 自研 babel 的原因:

1. **消息总线**:采集器与引擎之间、引擎与消费方之间的解耦
2. **事件持久化**:retention 期内的事件可重放,不需要像 1.x 那样额外落一份磁盘文件
3. **回溯能力**:从任意 offset 重放,用于策略上线前的历史验证

主要 topic:

| topic | 内容 | 生产者 → 消费者 |
|---|---|---|
| `nebula.events` | 标准化业务事件 | collector → engine |
| `nebula.notice` | 风险告警 | engine → console-api / 业务系统 |
| `nebula.profile` | 画像更新 | engine → engine(反馈回路) |

### engine —— 计算

单个 Flink 作业内包含三条逻辑链路:

**① 变量引擎**。按变量定义构建计算图。每个变量对应一类算子,`aggregate` / `sequence` / `dual` / `top` 是有状态算子,状态存于 RocksDB 并纳入 Checkpoint。图的构建顺序由变量间的引用关系拓扑排序决定;引用成环时在配置保存阶段即被拒绝。

**② 规则引擎**。策略条件求值。简单的阈值比较直接求值;复杂逻辑走 CEL 沙箱;跨事件的序列模式走 Flink CEP。命中后产出告警并写入名单。

**③ 画像更新**。维护长期行为基线(`profile` 模块的变量),写入 Redis 热层与 ClickHouse 冷层。

三条链路在同一作业内的原因:它们共享同一份事件流与同一套状态,拆成多个作业会引入跨作业的状态同步问题——这正是 1.x 双引擎的教训。

### 存储

| 组件 | 用途 | 关键设计 |
|---|---|---|
| **ClickHouse** | 事件明细、小时聚合、画像冷层 | 按天分区 + TTL 自动过期;小时聚合用物化视图,不需要额外的批任务 |
| **PostgreSQL** | 策略、变量、事件模型、用户与权限、审计日志 | 策略与变量以 JSONB 存储,可按内容检索;告警表按时间分区 |
| **Redis / Valkey** | 黑白名单、画像热层 | 名单以 TTL 自动失效,不需要清理任务 |

## 控制面

### console-api

合并了 1.x 的三个服务(`apiserver` 自研 Netty 框架、`nebula_web` Tornado、`nebula_query_web` Flask)。合并的理由不只是简化部署:这三者当年分别用两种语言实现,各自维护一份领域模型,是模型漂移的直接来源。

对外提供两类接口:

- **管理接口**:策略与变量的增删改查、名单管理、报表查询。需要认证与授权,全部写操作记入审计日志。
- **`/checkRisk` 同步查询**:供业务系统在关键动作(登录、下单、支付)前查询风险结论。这是**延迟敏感**路径,直接查 Redis,不经过数据库。

### console-web

管理界面。策略编辑器的表单校验规则由 `domain-schema` 生成,与后端校验同源——避免前端放行了后端拒绝的配置。

## 元数据的下发

策略与变量在控制面编辑后,需要让计算引擎生效。1.x 的做法是引擎定时轮询 Web 端的 HTTP 接口(带一个硬编码的 auth token)。

2.0 改为**通过 Kafka 广播元数据变更**,引擎订阅并热更新计算图。这样做的好处:变更即时生效而非等待轮询间隔;引擎重启时可从 topic 重建完整元数据;不需要引擎反向依赖控制面的可用性。

元数据变更是**版本化**的,每次变更产生一个版本号。告警中记录产生它的元数据版本,便于回溯"这条告警是在哪版策略下产生的"。

## 两种部署形态

同一份代码,两种拓扑。

### Lite 模式

面向中小规模与评估试用。`docker compose up` 一条命令,约 8GB 内存。

| 组件 | 形态 |
|---|---|
| Flink | standalone 单 JVM,状态存本地 RocksDB |
| Kafka | 单节点 Redpanda(协议兼容,资源占用低) |
| ClickHouse | 单节点 |
| PostgreSQL / Redis | 单节点 |

### Cluster 模式

面向大流量生产环境。Flink 走 Kubernetes Operator,Kafka / ClickHouse 集群化,按流量水平扩展。

**不提供第三种"轻量特化实现"。** 保持单一实现是刻意的取舍——1.x 用两套引擎换取轻量部署,代价是两套语义永久不一致。

## 可观测性

全部组件通过 OpenTelemetry 输出指标与链路追踪,由 Prometheus 采集、官方 Grafana 展示。

1.x 在这块自研了一套 metrics 框架,并把 Grafana 魔改后内嵌进管理后台。2.0 使用标准组件且不做修改,原因是可观测性栈的演进速度远快于本项目,绑定魔改版本会持续付出升级成本。

关键指标:

| 类别 | 指标 |
|---|---|
| 采集 | 各驱动的事件速率、解析失败率、脱敏规则命中率 |
| 计算 | 端到端延迟、Checkpoint 时长与失败次数、反压状态、迟到事件量 |
| 策略 | 各策略命中率、告警产出速率、名单规模 |
| 查询 | `/checkRisk` 的 P99 延迟与 QPS |

**迟到事件量**是一个需要重点关注的指标:它持续偏高说明采集侧的时间戳有问题或网络存在积压,而在 1.x 中这类事件被静默丢弃,无从发现。
