# ADR-0002:以 Flink 统一实时与离线两套计算引擎

- **状态**:已接受
- **日期**:2026-07
- **相关**:[ADR-0001](0001-rewrite-instead-of-upgrade.md)

## 背景

Nebula 1.x 有**两套独立的计算引擎**,语义并不一致:

| | greyhound(实时) | bordercollie(离线,即 offline 仓库) |
|---|---|---|
| 实现 | 基于 Esper 6.1 的 CEP | 自研变量 DAG 引擎 |
| 窗口 | 1 分钟粒度、5 分钟滑动 | 1 小时滚动,整点对齐 |
| 去重计数 | Esper 原生 `count(distinct)`,精确 | 前 20 精确 + HyperLogLog(log2m=9),误差约 4.6% |
| 状态 | 进程内存 | 进程内存 + 每小时落 LevelDB |

同一个"去重计数"的语义,在两套引擎上会算出不同的数。

更关键的是,1.x 必须**每小时用 cron 重放一遍全部事件日志**来重算离线变量。追查代码后可以确认这不是设计选择,而是对四个缺陷的补偿:

1. 在线引擎对迟到事件直接丢弃(`SlotEngine.add()` 中 `eventWindowId < currentId` 时返回 -1),没有 allowedLateness 机制
2. 在线引擎算不过来时主动丢事件(生产配置 `engine.mode.wait=false`),而 cron 进程强制把该参数覆盖为 `true`
3. 在线进程重启会丢失当前小时的全部状态,只能靠日志重放恢复
4. 在线侧只提供"当前小时"的查询接口,历史小时在线侧根本查不到

这套补偿机制自身还带来一个副作用:每小时 0~2 分钟存在**数据空窗**——上一小时的在线状态已被清空,离线结果尚未产出,此时查询返回空。

## 决策

**采用 Apache Flink 作为唯一计算引擎,取消离线重算层。**

实时变量与小时变量都由 Flink 作业计算,窗口类型由变量元数据的 `period` 声明,引擎按声明选择滑动窗口或滚动窗口。

## 理由

### 1. Flink 从根本上消除了离线重算存在的原因

上述四个缺陷逐一对应 Flink 的原生能力:

| 1.x 缺陷 | Flink 对应能力 |
|---|---|
| 迟到事件丢弃 | 事件时间语义 + `allowedLateness` + 侧输出流 |
| 过载丢事件 | 反压机制,上游自动降速而非丢数据 |
| 重启丢状态 | RocksDB 状态后端 + Checkpoint |
| 历史不可查 | 状态可查询,历史结果落 ClickHouse |

取消离线重算之后:少一层计算、少一套存储(LevelDB)、少一个 cron、少一个数据空窗期、查询路径从"当前小时查在线、历史小时查离线"的二选一简化为单一路径。

原本"重放历史数据"的能力并没有丢失,而是从**被迫每小时执行**变成**按需触发**——从 Kafka 或 ClickHouse 重放任意时间段,用于策略上线前的回溯验证。这反而是 1.x 没有、而风控运营最需要的能力。

### 2. 摆脱 Esper 的 GPL 许可

Esper 社区版采用 **GPLv2**。对于计划以 Apache-2.0 发布、且存在商业版本的产品,这是实际的法律风险。Flink 是 Apache-2.0。

替代方案上,Flink SQL 覆盖窗口聚合,Flink CEP 覆盖序列检测。值得说明的是,CEP 的能力**强于** 1.x 的现状:1.x 的序列检测并非用 Esper 的 `pattern` 或 `match_recognize` 实现,而是用 `std:groupwin(key).win:length(2)` 配合 `last(prop, 0) - last(prop, 1)` 的变通写法,实际只支持"相邻两次事件求差"这一种模式。

### 3. 一致性由单一实现保证

两套引擎的语义漂移无法靠文档或测试根治,只能靠合并实现来根治。统一后,`distinct_count` 等算子只有一份定义。

## 代价与应对

**Flink 比 1.x 的单机进程重。** 这与星云"轻量部署"的产品定位存在张力。

应对方式是提供两种部署形态,**共用同一份作业代码**:

- **Lite 模式**:Flink standalone 单 JVM + 内嵌 RocksDB,配合单节点 Redpanda 与单节点 ClickHouse,`docker compose up` 一条命令启动,资源占用约 8GB 内存
- **Cluster 模式**:Flink Kubernetes Operator,按流量水平扩展

不做两套实现——那会把刚刚消除的"双引擎语义漂移"问题以另一种形式重新引入。

**运维复杂度上升。** 需要提供 Flink 层面的监控指标、Checkpoint 失败告警、以及作业升级(Savepoint)的标准流程,这些纳入[运维手册](../operations/)。

## 后果

- `offline` 组件在 2.0 中不存在
- `greyhound`、`online` 合并为单一的 `apps/engine`
- 去重计数与标准差的语义发生变化,构成迁移时的两处不兼容,见[迁移指南](../migration/from-1x.md)
- 新增能力:任意时间段重放、精确一次语义、水平扩展
