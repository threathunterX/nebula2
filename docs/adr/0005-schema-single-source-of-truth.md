# ADR-0005:领域模型以 JSON Schema 为单一真相源

- **状态**:已接受
- **日期**:2026-07

## 背景

1.x 的领域模型在两处独立实现:Python 的 `nebula_meta`(供 Web 控制台与配置校验)和 Java 的 `com.threathunter.variable`(供计算引擎)。两者随时间漂移,最终形成一个系统性缺陷:**元数据层声明的能力远多于引擎实际实现的能力**。

实测差距:

| 类别 | 配置层声明 | 离线引擎实现 |
|---|---|---|
| 字符串条件算子 | `== != contains startwith endwith regex in containsby empty` 等 20+ 个 | 仅 `contains` / `equals` / `notEquals` |
| 数值条件算子 | `== != > < >= <=` | Long 仅 `> >= < ==`;Double 仅 `<` |
| 聚合函数 | `max min sum count avg stddev distinct_count top ...` | `max` / `range` / `amplitude` / `distinct_count` 未实现,调用时抛异常 |
| IP 地理条件 | 4 个算子 | 生成器直接返回 null,完全不生效 |

后果是用户在界面上配得出来的变量,引擎跑不了,且失败发生在运行时而非配置时。

## 决策

**领域模型只在 `packages/domain-schema/` 中用 JSON Schema 定义一次**,其余全部由它派生:

- Java 类型(计算引擎、控制面 API)—— 代码生成
- TypeScript 类型(前端)—— 代码生成
- 数据库 DDL —— 代码生成
- 文档中的字段与算子参考 —— 文档生成
- `seeds/` 资产的合规性校验 —— schema 校验

并配套三条强制机制:

1. **声明即实现**:schema 中声明的每个算子必须有实现与测试,CI 校验覆盖率必须为 100%,否则构建失败
2. **配置期校验**:变量与策略保存时即完成类型推导与算子合法性检查
3. **禁止手写模型类**:生成的类型文件纳入 CI 一致性检查,手工修改会被检出

## 理由

漂移是无法靠纪律或文档避免的——1.x 的两份实现在最初是一致的。唯一可靠的办法是让"两份"在结构上不可能存在。

选择 JSON Schema 而非 Protobuf 或 Avro 的原因:领域模型本身就以 JSON 形式存储和传输(策略配置、变量定义),JSON Schema 可以直接校验存量数据;且它对"条件算子的合法取值随字段类型变化"这类约束有原生表达能力(`if/then`、`allOf`)。

## 后果

- 新增一个算子的成本上升(需要同时提供 schema 声明、实现、测试),这是刻意的
- 前端的表单校验规则可以由 schema 自动生成,减少一处重复
- 文档中的算子表不会再与代码脱节
