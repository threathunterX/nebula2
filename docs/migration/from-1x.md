# 从 Nebula 1.x 迁移到 2.0

> 本文假设你熟悉 1.x 的使用。如果你是新用户,请直接看[快速开始](../guide/quickstart.md)。

## 迁移的本质

2.0 是**重写**,不是升级。没有原地升级路径,两套系统的存储、进程模型、依赖组件完全不同。迁移指的是:**把 1.x 的风控资产(事件、变量、策略)搬到 2.0,历史数据不迁移**。

这样设计的原因在 [ADR-0001](../adr/0001-rewrite-instead-of-upgrade.md) 有完整论证,简单说:1.x 依赖的技术栈(Python 2、OpenResty 1.11、Esper 6、Aerospike、自研 RPC 与存储格式)已整体 EOL,逐步升级的成本高于重写,且无法解决架构层面的历史包袱。

## 资产迁移

```bash
# 从 1.x 的 MySQL 导出并转换为 2.0 的 seeds 格式
nebula-migrate export \
  --source mysql://user:pass@1x-host:3306/nebula \
  --output ./my-assets

# 校验(检查 schema 合规性、算子可用性、引用完整性)
nebula-migrate validate ./my-assets

# 导入 2.0
nebula-migrate import ./my-assets --target http://localhost:8080
```

> 🚧 工具实现中。

`validate` 会报告三类问题:schema 不合规、引用了 2.0 未实现的算子、以及下文"语义差异"涉及的变量清单。

## ⚠️ 六处语义差异

这是迁移中**最需要注意**的部分。以下差异会导致同一份数据在 1.x 与 2.0 上算出不同结果。它们都是有意为之——修正 1.x 的缺陷或简化架构——但你需要知道差在哪。

### 1. 去重计数(distinct_count)精度

**1.x 行为**:采用"前 20 个精确 + 溢出走 HyperLogLog"的混合结构。HLL 参数为 `log2m=9, regwidth=5`,即 512 个 register,标准误差约 **4.6%**。更麻烦的是,小集合用 `String.hashCode()` 计算哈希,溢出进 HLL 后改用 `murmur3_32`,两种哈希混用。此外跨小时合并时对集合只做 `addAll` 不去重,会**系统性高估**。

**2.0 行为**:默认**精确去重**;基数超过阈值(默认 10 万)自动降级为 HLL,参数为 `log2m=14`,标准误差约 **0.8%**,并在结果中标记为近似值。可通过变量的 `function.config.distinct_mode` 显式指定 `exact` 或 `approx`。

**影响**:所有 `distinct_count` 类变量(1.x 内置资产中约 60 个)的历史值与新值**不可直接比较**。基于这些变量的策略阈值需要重新校准——通常 2.0 的值会略低于 1.x(因为消除了高估)。

**建议**:迁移后用真实流量并行运行 1~2 周,对比两边数值再调整阈值。

### 2. `stddev` 的定义

**1.x 行为**:名为 `stddev` 的算子实际返回的是**方差**(variance),计算式 `(squareSum - sum*avg) / (count-1)`,**没有开平方**。而变异系数 `cv` 里才做了 `Math.sqrt`。

**2.0 行为**:`stddev` 返回真正的标准差(方差的平方根),同时提供独立的 `variance` 算子。

**影响**:使用 `stddev` 的变量,新值约等于旧值的平方根,量级差异明显。

**迁移工具处理**:自动把 1.x 的 `stddev` 变量映射为 2.0 的 `variance`,保持结果一致。如果你希望改用真正的标准差,需手动改回并重新校准阈值。

### 3. 离线重算已取消

**1.x 行为**:每小时第 2 分钟跑一次 cron,重放上一小时的全部事件日志,重新计算所有 slot 变量。存在的原因是在线引擎有四个硬伤:迟到事件直接丢弃(无 allowedLateness)、算不过来时主动丢事件、进程重启丢失当前小时状态、历史小时在线侧无查询接口。

副作用是每小时 0~2 分存在**数据空窗**(上一小时的在线状态已清空,离线结果还没产出),此时查询返回空。

**2.0 行为**:Flink 的事件时间语义、allowedLateness + 侧输出、RocksDB 状态后端与 Checkpoint 从根本上解决了上述四个问题,**离线重算层整体取消**。查询路径统一,不再有"当前小时查在线、历史小时查离线"的二选一逻辑,也不再有数据空窗。

**影响**:架构简化,但如果你的运维流程依赖 `/data/persistent` 目录或离线 cron 的产出,需要调整。历史数据回溯改为从 Kafka 或 ClickHouse **重放**,这是 2.0 新增能力,可用于策略上线前的回溯验证。

### 4. 策略条件支持嵌套布尔

**1.x 行为**:策略由若干 term 组成,term 之间**只能是 AND 关系**,不支持 OR 和嵌套。想表达"A 且 (B 或 C)"只能拆成两条策略。

**2.0 行为**:条件是一棵可任意嵌套的布尔树,支持 `and` / `or` / `not`。

**影响**:向后兼容。1.x 策略迁移后表现为单层 `and`,语义完全等价,无需改动。

### 5. 风险分与处置动作真正落地

**1.x 现状**:170 条内置策略的 `decision` **全部是 `review`**,`score` 有 **169 条是 0**(唯一的例外 `设备请求下单行为单一` 为 1,应属遗留噪声而非有意赋值)。也就是说风险评分和自动处置这两项能力当年设计了但没有落地,系统实际只能产出"待人工审核"的告警。

**2.0 行为**:`score` 参与风险分计算(策略权重 × 命中次数 × 时间衰减);新增 `action.handlers`,支持阻断、二次验证、限流、降级、通知、Webhook 等处置动作。

**影响**:迁移后所有策略仍为 `review` + `score=0`,行为与 1.x 一致。要启用新能力需要显式配置。建议先在 `test` 状态下观察一段时间再切到 `online`。

### 6. 告警可解释性

**1.x 现状**:`notice.variable_values` 字段(设计用途是保存触发时的变量值快照)在代码里被写死为空字符串,从未真正落地。运营人员看到"IP 多次登录失败"的告警,却看不到当时到底失败了多少次。

**2.0 行为**:`explain` 默认开启,告警中包含触发时全部相关变量的值快照与阈值对比。

**影响**:纯增强,无兼容性问题。告警存储体积会略有增加。

## 策略结构的变化

1.x 的策略是一个扁平的 `terms` 数组,条款之间隐含 AND 关系,其中一条实际上是处置动作(`setblacklist`)而不是条件。2.0 把两者分开:`condition` 是一棵可嵌套的布尔树,`action` 是独立的处置对象。

迁移工具自动完成映射,你不需要手工改写:

| 1.x 条款 | 2.0 |
|---|---|
| `event` | 比较条件,左值为事件字段 |
| `func:count` | 比较条件,左值为内联计数器 |
| `func:getvariable` | 比较条件,左值为变量引用 |
| `func:setblacklist` | `action` 处置对象 |
| `func:sleep` | 策略级 `delay` 字段(延迟求值) |
| `func:time` | CEL 表达式 `inTimeWindow(start, end)` |
| `func:getlocation` | CEL 表达式 `ipLocation(ip, level)` |

两点值得注意:

**内联计数器的分组对齐条件会被丢弃。** 1.x 的计数器 `condition` 数组里混着形如 `{"left":"c_ip","op":"=","right":"c_ip"}` 的元素,它不是过滤条件,而是表达"按 c_ip 分组"——2.0 中这由 `groupby` 表达。如果照搬会变成一条恒真的无意义过滤。

**常量值保持字符串形态。** 1.x 把阈值 `5` 存为 `"5"`,迁移时不做类型推断,由引擎按左值类型转换。过早推断会出错。

CEL 函数的定义见 [CEL 表达式参考](../guide/cel-reference.md) 与 [`packages/cel-functions/`](../../packages/cel-functions/)。

## 策略模板的生效状态已被规范化

从 1.x 导出的 170 条策略携带了当年生产实例的生效时间窗与运行状态,直接分发会踩两个坑,2.0 的 seeds 已做规范化:

| | 1.x 原值 | 2.0 seeds | 原因 |
|---|---|---|---|
| 生效截止时间 | **170 条全部已过期**(2017-10-27 ~ 2024-01-06) | 清空(长期有效) | 照原样导入,每条策略都处于已过期状态,**一条都不会触发,而且没有任何提示** |
| 状态 | 全部 `online` | 全部 `test` | 清空时间窗后若仍为 `online`,导入即全量生效,可能瞬间产生告警洪水 |

`test` 状态的策略照常计算并产出告警,但告警标记 `test=true`,不参与线上决策。这与本文末尾建议的迁移节奏一致:先观察、校准阈值,再逐条切到 `online`。

> 如果你是从自己的 1.x 实例导出策略(而非使用内置模板),`nebula-migrate` 会保留你的原始状态与时间窗,但会对**已过期的策略发出警告**——这类策略在 1.x 里同样早已不生效,值得确认是有意为之还是被遗忘了。

## 对外契约的兼容性

以下保持**完全兼容**,业务系统无需改动:

- `/checkRisk` 同步查询接口的请求与响应结构
- `decision`(accept/review/reject)、`scene`(六大场景)、`check_type`(IP/USER/DeviceID/OrderID)三组枚举
- 17 个内置事件的名称与字段
- 变量命名规范

## 建议的迁移节奏

1. **并行期**:2.0 与 1.x 同时接入同一份流量,2.0 全部策略置为 `test` 状态,只观察不决策
2. **校准期**:对比两边告警量与变量数值,重点关注上面差异 1 和 2 涉及的变量,调整阈值
3. **切换期**:分场景逐步把 2.0 策略切到 `online`,1.x 对应策略下线
4. **退役期**:1.x 停止接收流量,历史数据按保留期自然过期或单独归档

不建议一次性切换。风控系统的阈值高度依赖业务流量特征,并行校准这一步省不掉。
