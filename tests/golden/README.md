# Golden 回归测试 —— 证明语义继承是正确的

2.0 重写了引擎,但必须保证从 1.x 继承的 253 个变量算出来的结果**仍然是对的**。这件事不能靠人工审阅代码,只能靠对照测试。

本目录定义这套对照机制。

## 核心方法

```
        ┌─────────────────┐
        │  合成事件序列    │  确定性、可复现、无真实数据
        └────────┬────────┘
                 ├──────────────▶ 1.x 引擎(容器化)──▶ 结果 A
                 └──────────────▶ 2.0 引擎         ──▶ 结果 B
                                                        │
                              逐变量比对 ◀───────────────┘
                                    │
                    ┌───────────────┴───────────────┐
                    ▼                               ▼
              完全一致 ✓                    存在差异
                                                    │
                            ┌───────────────────────┴──────────┐
                            ▼                                  ▼
              能被已知语义变更解释 ✓              不能解释 ✗ → 缺陷
```

**判定标准**:差异必须能被 [算子语义规格](../../docs/reference/operators.md) 中标注的语义变更解释。不能解释的差异一律视为 2.0 的缺陷,而不是"1.x 本来就有问题"——即使 1.x 确实有问题,也要先确认差异的成因与预期一致。

## 已知的、允许的差异

以下差异是 2.0 的有意变更,比对时按对应规则豁免。完整说明见[迁移指南](../../docs/migration/from-1x.md)。

| 编号 | 差异 | 涉及变量 | 豁免规则 |
|---|---|---|---|
| D1 | 去重计数精度(1.x 为「前 20 精确 + HLL(log2m=9)」混合,2.0 默认精确) | 全部 `distinct_count` 类 | 2.0 结果应 **≤** 1.x 结果;且在基数 ≤ 20 时**必须完全相等** |
| D2 | `stddev` 语义(1.x 返回方差) | 全部 `stddev` 类 | 2.0 的 `variance` 应与 1.x 的 `stddev` **完全相等** |
| D3 | `first` / `last` 依据事件时间(1.x 为到达顺序) | 全部 `first` / `last` / `lastn` 类 | 事件**有序**注入时必须完全相等;乱序注入时允许不同 |
| D4 | 迟到事件不再丢弃 | 全部有窗口变量 | 无迟到事件的用例必须完全相等 |
| D5 | TopN 的稳定排序 | 全部 `top` 类 | 值互不相同时必须完全相等;存在同值时按 2.0 规则比对 |
| D6 | 多分组键的 `sequence`(1.x 实现有缺陷) | `sequence` 类 | 单分组键必须相等;多分组键以 2.0 为准 |

> **D1 的边界条件值得单独强调**:基数不超过 20 时,1.x 走的是精确路径,两边必须完全相等。这条约束能有效验证 2.0 的精确模式实现无误——如果小基数都对不上,说明问题不在精度模式而在算子本身。

## 用例设计

用例放在 `cases/` 下,每个用例一个目录:

```
cases/<用例名>/
├── manifest.yaml      # 用例元信息:覆盖哪些变量、注入方式、豁免的差异编号
├── events.jsonl       # 合成事件序列(每行一条)
└── expected/          # 1.x 基线结果(由 capture 工具生成后固化)
```

### 用例必须覆盖的场景

| 类别 | 说明 |
|---|---|
| **算子逐个覆盖** | 每个聚合算子至少一个专用用例 |
| **窗口边界** | 事件恰好落在窗口切换点前后 |
| **空窗口** | 某个 key 在窗口内无数据 |
| **null 与类型异常** | 字段缺失、类型不符 |
| **基数边界** | 去重计数的基数为 19 / 20 / 21(跨越 1.x 的精确/近似分界) |
| **乱序与迟到** | 验证 D3、D4 的豁免边界 |
| **真实风险模式** | 撞库、批量注册、恶意下单等,端到端验证策略也能命中 |

### 合成数据的硬性要求

**用例数据必须全部合成,不得使用任何真实流量。**

- 域名使用 `example.com` 系
- IP 使用 RFC 5737 文档专用段(`198.51.100.0/24`、`203.0.113.0/24`)
- 手机号使用 `13800138000`
- 账号、设备 ID 使用可读的合成格式(`user_0001`、`device_0001`)

事件序列由生成器按固定随机种子产出,保证**可复现**。CI 中的 `check_no_pii.py` 会扫描本目录。

## 工具

> 🚧 实现中。

```bash
# 从容器化的 1.x 引擎捕获基线结果(仅需在新增用例时执行一次)
make golden-capture CASE=<用例名>

# 用 2.0 引擎运行全部用例并比对
make golden-verify

# 只跑某一个用例,输出逐变量的详细差异
make golden-verify CASE=<用例名> -- --verbose
```

`golden-capture` 依赖一个固定版本的 1.x 运行环境镜像。1.x 本身依赖 Python 2 与多个已不可用的私有包,因此该镜像需要独立构建并归档,不作为常规 CI 的一部分——**基线一旦固化就不再重新捕获**,除非确认此前的基线本身有误。

## 在 CI 中的位置

| 阶段 | 执行内容 |
|---|---|
| 每次 PR | `golden-verify`,全部用例必须通过 |
| 新增算子 | 必须同时新增覆盖该算子的用例,否则 schema 覆盖率检查失败 |
| 修改算子实现 | 若导致 golden 结果变化,PR 必须说明原因并更新豁免规则表 |

**豁免规则表的每次变更都需要在 PR 中显式论证。** 这张表是 2.0 与 1.x 之间语义差异的唯一权威清单,随意往里加条目等于放弃了对照测试的意义。
